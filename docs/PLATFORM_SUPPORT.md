# Platform support

Heliox runs on Windows, macOS and Linux. This page says what each part of the companion does on each system, where the code is, what the person has to grant or install, and how each claim is known. Nobody on the project develops on a Mac or a Linux desktop, so how a claim is known matters as much as the claim.

How each claim is known, everywhere on this page (one legend for every section and table):

- Run for real: it ran against the real system interface, and the page names what ran it. That is a GitHub-hosted runner (the CI job and the check's name, with the commit whose CI run it was) or the owner's Windows machine (with the date where it was recorded).
- Fakes only: only the decision logic ran, with the platform layer replaced by a fake.
- Not tested: nothing has run it.

A claim marked Fakes only or Not tested describes what the code is built to do, not what anyone has seen it do. Where one cell needs two markers, each part says which. "CI on 3793a0d" is the CI run on commit 3793a0d (12 November), and "CI on 0a8edad" the run on commit 0a8edad (run 43196949417), and "CI on e51aead" the run on commit e51aead (run 43209796125), and "CI on 008f1a0" the run on commit 008f1a0 (run 43213930595), and "CI on 105b573" the run on commit 105b573 (run 43219012295), and "CI on 8d513fd" the run on commit 8d513fd (run 43221495173), and "CI on e8bf67c" the run on commit e8bf67c (run 43228789151); their CHECK lines are quoted below.

## Reading the focused field

Every platform reader satisfies `FocusedTextSource` (`daemon/pilot/live/focused_text.py`): `read()`, `status()`, `close()` and `available`. `create_reader()` picks the one for the system. Each reader turns what its accessibility interface says about the focused element into `ElementFacts`, and `focused_text_policy.admit` makes the one decision for all three: text passes only from a writable field or a terminal, never from a secure field, and only the last 6,000 characters. The window-level rule, `never_read`, refuses Heliox's own window, password managers, the system credential stores (Keychain Access, Passwords, Seahorse, KDE Wallet) and apps the person excluded from the timeline before any reader runs. The decision itself: Fakes only, on all three systems; the secure field refused: Run for real (CI on 3793a0d, `macos/secure-field-refused`, `x11/password-refused`, `wayland/password-refused`).

Field identity has to stay the same while the person types and the window title changes:

- Windows: the UI Automation runtime id (Run for real on the owner's machine).
- macOS: the process id plus `CFHash` of the accessibility element, which hashes what the element refers to (Run for real: `macos/identity-stable-across-title-change`).
- Linux: the application's bus name plus the element's object path (Run for real: `x11/identity-stable-across-title-change`, `wayland/identity-stable-across-title-change`).

The unit tests check the property with fakes: the same field keeps its identity across typing and a title change, and a different field gets a different one.

Live drops a card early when the window its field lived in has closed. Windows asks whether the window handle in the UI Automation id still exists (Not tested on its own). macOS asks the Accessibility API about the field's window: its element must still answer, and its window (`kAXWindowAttribute`) must still be one of its app's windows (`kAXWindowsAttribute`, which counts a minimised window). Asking the element alone was not enough: in CI on 3793a0d the Mac's text field kept answering after its window closed (`macos/window-gone-after-close` failed), because the app was still running; with the fix, CI on 0a8edad: `macos/window-gone-after-close` passed (the element still answers, its window is no longer one of the app's): Run for real. Linux asks AT-SPI whether the field's object still exists (its application left the bus, or the object answers unknown or defunct): Run for real, `x11/window-gone-after-close` and `wayland/window-gone-after-close` passed in CI on 3793a0d. ### macOS

The reader uses pyobjc (`pip install 'pilot-daemon[macos]'`, included in `all`). pyobjc is Apple-platform-only, maintained, and ships prebuilt wheels, so nothing is compiled on the person's machine. It reads `AXFocusedUIElement` from the system-wide element with a 0.25 s messaging timeout, meant to keep a hung app from stalling Live (Run for real, CI on e8bf67c: with the field read before the hang, `macos/read-of-a-hung-app-returns-within-3s` passed while the app's main thread was held for 6 s; the fixture was already in front once the earlier one was ended. In CI on e51aead the check had read no field at all, so its pass then proved nothing). It refuses a field before reading its value when the subrole is `AXSecureTextField` (Run for real) or when secure keyboard entry is on (Fakes only). Terminal.app and iTerm2 are read as terminals (Fakes only). Other terminals expose nothing.

The Accessibility permission belongs to the app "Heliox-OS". The daemon is the app's child process, and macOS attributes a child's requests to the responsible app (Not tested: no run of the built app on a Mac). A daemon started from a terminal during development is attributed to that terminal.

Heliox checks the permission without a prompt (Run for real: `macos/permissions-read-without-prompt`). When it is missing, Live's settings say what to turn on and where, and offer one button that shows the system prompt; that prompt appears at most once per run; Heliox re-checks every 10 s, so turning the permission on takes effect without a restart (all Fakes only: the runner has the grant). Rebuilding the app with an ad-hoc signature can drop the grant.

`macos_permissions.snapshot()` reads microphone, Accessibility, Screen Recording and Automation without prompting. Accessibility and Screen Recording can only say "granted" or "not granted". `microphone_state()` is the interface the audio side uses.

### Linux

The reader speaks AT-SPI directly over D-Bus with jeepney (`pip install 'pilot-daemon[linux]'`, included in `all`). jeepney is pure Python and is already pulled in by SecretStorage. PyGObject and pyatspi were not used because a pip install of them needs a compiler and the cairo and GObject headers.

The reader subscribes to `object:state-changed:focused` events, so each read is four or five calls to the focused application. When no event has arrived, it searches the active window for the focused element, visiting at most 250 objects and searching at most every 3 s.

What the person needs:

- The AT-SPI bus (`at-spi2-core`). Without it, Live says the bus is not running and what to install (Fakes only).
- For Qt, Chromium, Electron and Firefox apps, toolkit accessibility turned on: `gsettings set org.gnome.desktop.interface toolkit-accessibility true`, then restart those apps. Live says this when the session reports accessibility off (Fakes only).

GTK 3 apps: Run for real (the fixture under X11 and sway). GTK 4 apps: typed text Run for real under X11 (CI on 008f1a0, `gtk4/reads-typed-text`). A hung GTK app: `x11/read-of-a-hung-app-returns-within-3s`, real check new in this round, result to come.

Password fields. GTK 3, Qt, Chromium, Electron and Firefox give a password field the role "password text"; GTK 4 does not. It names its roles after ARIA in GetRoleName, so a password entry is a "text box" like any entry, and it marks the password only in the numeric role (GetRole). In CI on 008f1a0 the reader read a GTK 4 password entry's text as an ordinary field. The dump from CI on 8d513fd shows the mark on the focused object itself: role name "text box", numeric role 40 (password text), inside a "generic" (39), inside the window. The reader asks the numeric role of the focused field, and of its two parents for toolkits or versions that mark only an enclosing entry. It refuses the field when any of them is a password, and whenever any role on the way cannot be read: only a walk that ends normally can say "not a password". Run for real under X11 (CI on 8d513fd: `gtk4/password-refused`, 17 of 17 reads refused, nothing leaked); under sway too (CI on 7f553b9: `gtk4-wayland/password-refused`, 17 of 17). The press path refuses a password field the same way. The snapshot never reads any field's value, only its role and label. GTK 4 also names its window "application" in GetRoleName (numeric role 23, a frame), so windows are now recognised by numeric role as well, which gives GTK 4 windows their title in the timeline and the never-read rules (Fakes only, from the same dump). Firefox: Run for real under X11 (CI on 7f553b9: `firefox/password-refused`, 17 of 17). GTK 4 under sway: Run for real in the same run, 17 of 17. Qt, Chrome and Electron: Run for real under X11 in CI on 052f815, 17 of 17 reads refused each (`qt-switch`, `qt-forced`, `chrome-forced-switch`, `electron-forced-switch`); on macOS, Chrome and Electron mark the password input with subrole AXSecureTextField and turn secure keyboard entry on (15 of 15 refused). A password input with no label, no name and a neutral id is refused the same way, by the system's own mark, on every target that can be read: Run for real in CI on 49bd35f (run 43337605746, `unnamed-password-refused`): on Linux 17 of 17 for Firefox, Chrome and Electron with the desktop switch, and Qt; on macOS every read refused (14 to 16 reads per target) for Safari, Chrome (enhanced and forced) and Electron; on Windows 17 of 17 for Edge and Chrome; nothing leaked anywhere.

Terminals (all Not tested by a run of the terminal itself through AT-SPI):

- Readable: VTE terminals (GNOME Terminal, Tilix, Terminator, Xfce Terminal).
- Partly readable: Konsole.
- Not readable: Alacritty, kitty, WezTerm, foot and xterm, which expose nothing.

AT-SPI does not depend on the display server: under sway it read the same as under X11 (Run for real); GNOME's and KDE's compositors: Not tested. `xdotool` remains the fallback for the window title on X11 when an app is not on the accessibility bus (Fakes only until `windows-x11/foreground-falls-back-to-xdotool` has run).

## Short commands during a task

While a task runs, a one-step command that is a system call runs at once beside it; one that is a key press, or
that brings a window to the front, waits for the task (it could land in the window the task is typing in), and
Heliox names it: "I'll open Notepad when this is done." (`pilot/conversation/quick.py`, `runs_beside_a_task`).

| Said | Windows | macOS | Linux |
|---|---|---|---|
| Volume up, volume down, louder, quieter, mute, unmute, set the volume to 30 | At once (Core Audio); waits when Core Audio does not answer | At once (`osascript`) | At once (`pactl`, else `amixer`); waits when neither is installed |
| Battery, disk, memory, processor, processes, system information | At once | At once | At once |
| Next track, previous track, play, pause | Waits: a media key press (SendInput), and Heliox cannot tell what the player did | Waits: a media key event, and Heliox cannot tell what the player did | At once, through the media player itself (MPRIS), saying what it reports ("Paused Spotify."); waits, as a key press, only without a session bus |
| Open an app or a site, search the web, switch to a window | Waits | Waits | Waits |

Media commands on Linux go to the player itself over MPRIS (`pilot/system/mpris.py`, through jeepney): the player
that is playing; with none playing, the only paused one; with none paused, the only player there is. No player:
"No media player is running." Two or more playing (or, with none playing, two or more paused): Heliox names them and
changes none. Fakes for the bus, and a real check against test players on a private session bus in
`platform-readers` (`mpris_check.py`). Windows and macOS still send a media key, which waits during a task, and the
sentence there says only what was asked, not what the player did. Their routes, not built:
- Windows: the system media transport controls, `GlobalSystemMediaTransportControlsSessionManager` (WinRT),
  `TryTogglePlayPauseAsync`, `TrySkipNextAsync`, `TrySkipPreviousAsync` on the current session. From Python this
  needs a WinRT binding (the `winrt` packages) or a PowerShell WinRT call, which is a new dependency or a script.
- macOS: the system's Now Playing control (MediaRemote) is a private framework with no supported API. The public
  routes are AppleScript to a named player (`tell application "Music" to playpause`, the same for Spotify), which
  needs Automation permission for each app, or the media key event Heliox sends today. That event is a
  system-defined event that the system hands to the Now Playing app rather than to the focused window, so it may be
  safe beside a task; that has not been tested.
