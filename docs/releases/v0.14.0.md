# Heliox OS v0.14.0 — Co-Adaptive Assistance and Governed Desktop Agency

v0.14.0 consolidates about 700 post-0.13 commits. Heliox now acts on real interface elements instead of pixels, keeps autonomous work across restarts, uses tools from your own MCP servers, listens while it works, and introduces a consented study of how a person, the interface and Heliox adapt to each other. Every new path keeps Heliox's deterministic permission and approval boundaries, and several of them are now stricter.

## Highlights

- **Assistance co-adaptation (opt-in research feature)** — A selection study inside Heliox's own window models the interaction between you, the interface and Heliox. For each kind of help (accept the click, a larger target, a confirm step, waiting for another try, asking which item you meant, suggesting another input) it predicts completion, corrections, unintended activations, time and your rated effort for you today, and chooses within rules you set. It changes presentation only, never approves or runs anything, and never commits an ambiguous selection by guessing. It is off by default; each purpose needs its own consent, data is encrypted with a per-participant key in the OS keyring, and revoking or erasing deletes the data and the key. Start it from Settings → Assistance & co-adaptation.
- **Accessibility-grounded desktop control** — Desktop clicks target elements from the accessibility tree instead of pixels, including WinForms and owner-drawn buttons; buttons can be pressed in the background without moving the cursor; browser actions use page snapshots and keep secrets with you. You can take the desktop back from Heliox at any time, and Heliox can hand it to you when it needs help. No virtual machine is involved.
- **Durable and scheduled autonomy** — Autonomous jobs survive daemon restarts and resume only when you ask. Scheduled runs are limited to an approved list of actions. A goal Heliox cannot reach is reported as blocked instead of being faked, and every tool call of background work appears as a card in chat.
- **Tools from your MCP servers** — Heliox can call tools from the MCP servers you list in `mcp_servers.json`. Read-only tools run directly, every other tool asks first, and Settings shows each server with a reload button.
- **Voice-first control while Heliox works** — Speaking during a task does what you mean: questions, corrections and a spoken "no" reach the running task. Background approval dialogs stay open while you keep working, the approval dialog shows what an action will actually run, and the world model reviews every autonomous plan.
- **Fail-closed settings and approvals** — Settings change safely while work runs and survive unreadable, locked or hand-edited config files, and every open window stays in step. An action family that a gateway profile does not list is read-only. An approval that is never answered, or whose reply never reaches the window, expires instead of running. A plan resumed after a restart runs only the actions you ticked. A gesture can approve only a dialog that has been visible for a second, and only the ticked actions.

## Reproducible evidence snapshot

- The generated catalog declares **162 action types** across **21 executable specialists** with provider coverage for every declared action; **22** actions have an independent post-condition verifier. This does not mean every action is available on every host or independently verified.
- The release benchmark measures **26.155 ms median** and **27.354 ms p95** for 100 guarded, steady-state CPU-status requests with **zero model calls**.
- Four real read-only status paths measured **26.122 ms CPU**, **3.082 ms memory**, **3.247 ms disk**, and **74.610 ms system-information** median latency across 50 iterations each.
- The deterministic dispatch regression passed **59/59** fixed cases with **0.023 ms median** routing latency.
- During a real one-second CPU monitor sample, the concurrent heartbeat's maximum interval was **16.651 ms**. This measures scheduler availability, not UI or hardware-input latency.
- The assistance co-adaptation quick benchmark ran on **simulated users only** (tuning families, in-sample, five per family). For simulated hand-pointer novices the adaptive engine scored **0.36** realized utility per trial against **−0.21** for the plain interface, with **13.9%** against **19.6%** unintended activations; for simulated precise mouse users the plain interface still scored higher (**1.11** against **0.90**). Every policy had **zero** actions on ambiguous input and **zero** rule violations. This is not evidence about people.

## Safety and privacy boundaries

- Assistance co-adaptation is a research feature. No result says it improves selection for people until the pre-registered human study in `daemon/benchmarks/coadaptation_protocol_v1.json` reports. It is not a medical or certified accessibility device, and EEG is not part of it.
- Learned components, including the co-adaptation model, the risk world model and the Gnomon reviewer, can add caution or change presentation but never grant permission, remove a deterministic warning or execute.
- Background desktop presses, MCP tools and scheduled runs go through the same permissions, gateway floors, approvals and verification as interactive commands.
- Neural intent remains an accessibility and research interface. Synthetic and recorded EEG evidence does not establish live brain control, human accuracy, medical use, or unrestricted thought decoding.
- Camera, gaze, gesture, microphone, speaker, accessibility permissions, first-run setup, and other hardware-dependent paths still require validation on the user's actual devices.
- SignPath test-policy signing is validated. Production signing remains dependent on the production certificate becoming usable and the release workflow being migrated to it.

## Upgrade guidance

Download the installer matching the operating system from the [v0.14.0 release](https://github.com/VyomKulshrestha/Heliox-OS/releases/tag/v0.14.0). Back up settings, allow first-run Chromium and daemon setup to complete, and re-check provider CLI login, integration credentials, microphone, camera, browser, local TTS, Air Handoff pairing, peer collaboration, MCP servers and optional model configuration after installation. Gateway profiles hand-edited in `config.toml` that leave out an action family now treat it as read-only; add the family explicitly if you relied on the old behaviour.
