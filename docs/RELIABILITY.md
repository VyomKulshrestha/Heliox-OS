# Reliability: what happens when something fails

This page lists the faults Heliox handles, what it does about each, what you see or hear, how it recovers, and what
has shown it. Every row names its tests; a behaviour without a test is listed under [Not covered](#not-covered), not
in the tables. Each row says which systems its tests ran on.

Every row carries one marker in its "Shown by" cell:

- **Run for real:** the fault was made to happen with the real thing: a killed process, a real socket or port, a
  real SQLite error, a real keychain, a real file system, a real start of the daemon on a CI runner. The cell says
  what ran it and on which systems; when only part of the row was shown this way, it says which part.
- **Fakes only:** tests with stand-ins for the GPU, the provider, the clock, the keychain or the failing write.
- **Not tested.**

**Drill** means a hand run on a real machine and always gives the machine and the date. **Result to come** marks a
real check that is in CI but has not reported yet; until it has, the row keeps the marker its other tests earned.

The Python tests (`daemon/tests/`) run in CI on ubuntu, macOS and Windows. The window's tests (`*.test.ts`, in
`tauri-app/ui/src/`) run in CI on ubuntu. The Rust unit tests (`tauri-app/src-tauri/`) run in CI on ubuntu and macOS;
on Windows CI compiles them without running them. The real checks are in `daemon/tests/platform_real/`: the "Real
faults" CI job (ubuntu, macOS, Windows, a fresh home for each step, never blocking) and the weekly soak workflow.

## The daemon itself

| Fault | What Heliox does | What you see or hear | How it recovers | Shown by | Tests |
|---|---|---|---|---|---|
| The daemon process exits or is killed while the app is open | The desktop app, which started it, starts it again after 2 s, doubling to 60 s between attempts. A daemon you started yourself from a terminal is never touched. | One line in the conversation: "Heliox's background service stopped. Starting it again in 2 s." The window reconnects by itself. | The back-off resets after five quiet minutes. | **Fakes only:** the back-off and the notice wording (Rust, ubuntu and macOS; vitest, ubuntu). The restart has never been run after a real crash, on any system. | `supervisor.rs` unit tests; `session.supervisor.test.ts` |
| The daemon stops answering (its event loop is stuck) | After a 300 s start-up grace, a minute without an answer to its ping counts as a hang: the app kills it and its direct children, then starts it again. | "Heliox's background service stopped answering, so it is being restarted." | As above. | **Fakes only:** counted ticks (Rust, ubuntu and macOS). A really stuck daemon has never been killed this way. | `supervisor.rs` (`a_minute_without_an_answer_after_start_up_is_a_hang`, `silence_during_start_up_is_not_a_hang`) |
| The computer sleeps and the clock jumps | The desktop app's hang rule counts its own 5 s checks, not clock time, so a jump never looks like a minute of silence. The daemon notices the wake itself, whether the monotonic clock stopped during sleep (Linux, macOS) or kept counting (Windows). It then closes every window that let speech count as meant for Heliox without the wake phrase (otherwise still open an hour later on Linux and macOS), stops the reply it was giving, and checks reminders at once. A wall clock set back is not a wake. | Speech after waking needs the wake phrase again. Reminders that came due during sleep arrive together ("While this computer was asleep, ..."). | Nothing to recover. | **Fakes only:** injected clocks (Python on all three systems; Rust on ubuntu and macOS). How each system's clocks behave in a real sleep is assumed, not observed. | `test_wake.py`; `supervisor.rs` |
| Start-up is slow (a loaded machine, a first run) | The daemon listens before its heavy start-up (after the data-folder check and the token files). `ping`, `health`, `ready` and `startup_status` answer without waiting for start-up, though a reply can wait up to about 0.3 s while one of start-up's constructors runs (measured on the development laptop); anything else waits until start-up has finished and is then answered as usual. | "Starting: opening Heliox's records" (then the next stage) instead of "Reconnecting...". | Becomes "Online" when ready. | A task was running when the daemon died | Nothing starts again by itself. Steps that may or may not have happened are marked uncertain and never repeated. | A card: "Heliox stopped while it was doing X. 1 step was done, 2 were left." with Continue (or "Plan it again") and Leave it. Voice can say "leave it" but never "continue". | Only your Continue button restarts it. Leave it writes a line to the activity log. A reconnect to the same, still-running daemon carries on as before. | **Run for real**, for what a hard kill leaves in the stores: a process holding the real task and checkpoint stores mid-task is killed (`taskkill /F`, SIGKILL), and the next start reports the task interrupted, 1 done, 2 left, 1 uncertain, with nothing run. In the Real faults job on ubuntu, macOS and Windows, CI on 008f1a0: passed. The card itself: fakes only (vitest). | `kill_checks.py` (`kill/interrupted-task`); `test_interrupted_task_offer.py`, `test_resume_partial_approval.py`; `session.interrupted.test.ts` |
| An approval was open when the connection dropped or the daemon stopped | Approvals fail closed: the dialog closes and nothing in it is approved. | "Lost the connection to Heliox, so the approval dialog was closed. Nothing in it was approved." | A task still waiting after the reconnect shows its approval again; it must be approved again. | **Fakes only:** the server objects in one process (all three systems); the dialog in vitest. No real socket was dropped mid-approval. | `test_pending_resolution_lock.py`, `test_confirmation_unanswered.py`; `session.confirm.test.ts` |
| The daemon is stopped while things are in flight | Speech stops first, then the conversation turn, then voice turns, then the running task, then the subsystems; requests still open are cancelled before any store closes. Each step waits at most 10 s and the whole stop at most 30 s; anything slower is logged and left behind. | Speech stops at once. | Not needed: stop() always completes. | **Run for real:** a real daemon with a model call in flight (a local port that never answers) exited 0.6 s (ubuntu), 1.3 s (macOS) and 0.6 s (Windows) after it was asked to stop, in the Real faults job, CI on 008f1a0. The order of the steps and their 10 s bounds: fakes only (all three systems). | `test_daemon_stop_releases_workers.py`, `test_server_background_lifecycle.py`; `stop_timing_check.py` |
| A second copy starts: the app is opened twice, or a daemon is already running from a checkout | The second copy claims the port (bound, not yet listening) before anything else. If the port is taken, it stops: it writes no tokens, opens no store and leaves the running copy alone. A copy that does start writes its token files before it listens, so a client that connects has read this run's token, never the last run's. Windows uses SO_EXCLUSIVEADDRUSE (never SO_REUSEADDR) on the claim; Linux and macOS use SO_REUSEADDR so a restart is not refused during TIME_WAIT, plus a per-port lock file so two copies started in the same instant cannot both pass the claim. Every address the host resolves to is served, as before. | "Heliox: Port 8785 is already in use, most likely by another copy of Heliox, so this copy did not start and left the running one alone. Close the other copy (or the program using that port) and start again." The process exits with code 3. | Use the copy that is running. | **Run for real:** a real socket holding the port and a real first copy whose token files stay byte-identical, on all three systems. Two real daemons started in the same instant, in the Real faults job on ubuntu and macOS, CI on 008f1a0: one exited with code 3 and the sentence after 0.8 s and 0.7 s, and the other answered with its own token files. | `test_second_copy.py`; `two_copies_check.py` |
| A second copy of the desktop app is opened, or the app starts while a daemon from a source checkout is starting | A second launch of the app brings the first window forward and exits (a per-person lock file, `app.lock` in `~/.config/heliox-os`, and a loopback port only the first copy's secret opens). A daemon the app starts that exits with code 3 ("another copy is serving") is not a crash: no restart, no alarm. | "Heliox's background service is already running from another copy; this window is using it." If that copy's port then stays silent for a minute: "The other copy of Heliox's background service stopped, so this app is starting its own." | Nothing to do. A developer who restarts a checkout daemon within a minute gets the port back; after that the app's own daemon holds it and the checkout daemon stops with the "already in use" sentence. | **Fakes only:** Rust unit tests on ubuntu and macOS. Never run as two real app launches; no real window has been brought forward. | `supervisor.rs` (exit 3, borrowing, take-over), `instance.rs` (lock, bring forward, a wrong secret, an absent first copy) |
| An update (or a repair) starts while the app is waiting to restart a daemon that stopped, or to take over from a copy that went silent | The supervisor's back-off ends as soon as setup pauses it, and it never starts a daemon while paused: before, a restart decided earlier started one from the environment being replaced (on Windows its files are locked, so the update was rolled back; elsewhere it held the port and the lock, so the updated daemon never started). When the pause ends, the app owns the daemon setup started, or quietly borrows the one that answers. | The update's own progress; no "background service stopped" line when the pause ends. | Nothing to do. | **Fakes only:** Rust unit tests on ubuntu and macOS. The update-path CI job runs `update.py` with no app, so it does not reach this. | `supervisor.rs` (back-off cut short by a pause, no launch while paused or exiting, ownership after the pause) |
| Start-up after months of use (a long experience ledger) | The online learner no longer replays the ledger before Heliox answers. It loads after ready, from its saved state (written every 2,000 events, at a clean stop and after a full replay), reading only the events after it; with 100,000 events and a state saved 5,000 ago that is 6 pages instead of 101, and it then decides exactly as a full replay does. The state is a pickle checked with HMAC-SHA256 and built only from an allow-list of classes; any mismatch (key, versions, a reset since) falls back to a full replay in the background. The key is a file, `keys/learner_snapshot_key` in the data folder beside the snapshot, made once, owner-only (the file 0600 in a 0700 folder; on Windows the person's own profile folder), so it survives a reboot; a file other users can read is refused. A key an earlier version kept in the runtime folder (which Linux empties at every reboot and macOS keeps under Library/Caches) is moved there on start when it signs the saved state. It is never written to the system keyring (a keychain write can wait on a dialog nobody sees); a key an earlier version kept there is still used if the keyring answers within 1 s. Until the learner has loaded, the risk gate first holds its decision for it: up to 5 s from when it is asked, and not at all when the learner has said it needs longer (it estimates from how many events it has to read). Only a learner still loading after that gets the approval it could have added. Proactive suggestions wait. The key catches a saved state that is truncated, corrupted, from another version, or copied on its own from another machine or a backup made under another key, and other users of the computer. It does not stop a program already running as this user, which can read the key (against that, only the allow-list of classes stands), and a copy of the whole data folder carries the key with it. | While a decision waits: "One moment, Heliox is still starting.", once, aloud and in the window. An approval that appears anyway says "Heliox was still loading what it has learned from past outcomes, so it asks for your approval to be safe." | Nothing to do; for a refused key file, `chmod 600` as the log says. | **Run for real:** the CI first-run job starts a daemon over 100,000 seeded events, once with a saved state and once replaying in full, on all three systems ([below](#how-long-start-up-takes)). That the saved state decides as a full replay does: fakes only (a synthetic ledger). The key surviving an emptied runtime folder and an earlier key being moved: real daemons over 5,000 events in the Real faults job on all three systems, result to come. The 5 s wait and its sentence have not been heard on a real start. | `test_learner_snapshot.py`, `test_learner_key_file.py`, `test_late_start.py`, `test_learner_wait.py`; `learner_key_reboot_check.py`; `test_startup_stages.py` counts no ledger read before ready; `seed_ledger.py`. A decision made on the event loop's own thread does not wait (it would hold up the loading). |
| A request reaches a part that starts after ready (neural input, agent mesh history, prompt improver, strategy evolution, evolution harness, long-term preferences, screen awareness, proactive suggestions) | They start after ready in the order a person needs them: screen awareness, long-term preferences and strategy evolution (every plan reads them), then proactive suggestions and the prompt improver, 0.5 s apart; neural input, the agent mesh and the evolution harness last, each once no request is running (at most 60 s later). A request that needs a part not started yet starts it at once, out of turn, and waits for it: at most 5 s for a request for the part, at most 2 s for a plan, which waits for the three parts it reads together. Two requests for the same part share one start. None holds the event loop for 100 ms or more. A plan made while a part is still starting after its bound leaves out what the part adds, as before. | Only a part still starting after the bound answers with its sentence, for example "Strategy evolution is still starting; until it has, plans use the standard planner instructions. Ask again in a moment." A part that fails says so and Heliox carries on without it. | Ask again; the window asks again by itself when the daemon announces the part (late_parts). | **Run for real**, for the start before this change: every late part started 15.2 to 25.7 s after the process began, on all three systems in the CI first-run job, nearly all of it the 2 s pauses. The on-demand start and the new order: fakes only (in one process); the first-run job now prints when each part settled and how long a request for each of the three most-used parts waited when sent 1 s after ready: result to come. | `test_late_start.py`; `test_start_loop_steps.py` |
| An update finds a daemon still running that the app only borrowed (quitting the app would not stop it) | If it accepts this installation's window token it is Heliox's: the update asks it to stop through its `daemon_stop` RPC and waits up to 30 s for the port. Anything else, or an older Heliox without that RPC, is named and left alone: the update never ends a process it did not start. | "Port 8785 is held by python.exe (process 40212). Open Task Manager (Ctrl+Shift+Esc), go to Details, select process 40212 and choose End task. Then start the update again." (Activity Monitor on macOS; the system monitor or `kill` on Linux.) | Stop it as the sentence says, or let the update stop Heliox's own. | **Run for real:** a real daemon stopped with its token, and a wrong token and a non-Heliox server left alone, on all three systems. Naming a program that is not Heliox from the live netstat, lsof or ss: In the Real faults job, CI on 008f1a0: passed on macOS and Windows (the update stopped in 0.3 s and named the program); on ubuntu the stand-in program could not take the port, most likely because the earlier steps' connections were still in TIME_WAIT, so the check now binds as the daemon does and says who holds the port: result to come. | `test_update_borrowed_daemon.py`; `foreign_port_check.py` |
| The system credential store does not answer: a macOS keychain waiting on a dialog nobody sees (no login keychain, a locked keychain, a permission prompt), or a Secret Service that hangs | Every get, set and delete runs in a thread of its own and is given up on after 3 s (`pilot.security.keyring_guard`); for the next 5 minutes calls fail at once instead of piling up. The key vault waits for it in a worker thread, so the event loop never waits on the keychain, and the recording and study key stores wait at most 3 s once. The learner's snapshot key is never written to the keychain. Before this, the daemon froze right after it started listening on macOS (2e0e58b to 0a8edad). | Once in the log and in the review status (`autonomy_review_status`, `credential_store`): "The system credential store (Keychain, Credential Manager or Secret Service) did not answer within 3 s, so Heliox carried on without it: saved API keys and other secrets cannot be read or saved until it does. A locked keychain made for the check, on macOS in the Real faults job: result to come. A keyring that never answers: fakes only (all three systems). | `test_keyring_stall.py`; `keychain_locked_check.py` |
| A request arrives while the daemon builds its parts (before ready) or in the first seconds after ready | The heavy imports run in worker threads (start-up's own list, the learner's numerical libraries, neural input's), so the event loop keeps answering. After ready no step of Heliox's uses 100 ms or more of the processor (before this, importing the learner's libraries held the loop 1.6 s right after ready), and the learner's replay hands the loop back every 50 events (a page of a thousand was learned in one step). Before ready, the constructors initialize() runs between its awaits still hold it for up to about 0.3 s at a time on the development laptop (spread over many small parts, none over 30 ms when sampled): a `ping` or `startup_status` sent then waits that long. | Nothing: the badge says "Starting: <stage>". | Nothing to do. | **Run for real:** a real start over a seeded ledger, every step of the loop timed with the loop thread's processor time and named, on all three systems (processor time, because a busy machine made any step look slow in wall time). The 0.3 s before ready was measured on the development laptop only. | `test_start_loop_steps.py` |
| The config file is half written, has a key from a newer version, or cannot be opened | Heliox starts on the defaults and keeps a copy of the file. It never rewrites your file: saving is refused until you fix it or choose Reset to defaults. | Settings shows "config.toml could not be read (<what was wrong>). ### How long start-up takes

GitHub runner, first run from an empty home. CI on 008f1a0: ubuntu-24.04, macos-latest and windows-latest, each
with the runner's Python and with a private one (six combinations). Seconds after the daemon's process started,
as the daemon itself records them (`HELIOX_STARTUP_TIMINGS=1`); the range is the fastest and slowest of the six.
The two lower rows start from a home seeded with 100,000 experience-ledger events (`seed_ledger.py`).

| Start | Listening | Ready | Learner loaded | Every late part started | Modules loaded at ready |
|---|---|---|---|---|---|
| First run, empty home | 0.2 to 1.1 | 1.3 to 2.9 | 1.8 to 5.6 | 15.9 to 20.2 | 1,159 to 1,166 (2,591 to 2,667 once every part has started) |
| 100,000 events, saved state | 0.2 to 0.7 | 0.6 to 1.6 | 1.1 to 3.1 | 15.2 to 17.6 | 954 to 961 |
| 100,000 events, full replay | 0.2 to 0.7 | 0.7 to 2.0 | 2.6 to 11.1 | 16.8 to 25.7 | 954 to 961 |

None of scipy, sklearn, pandas, river or torch is loaded at ready, on any of the eighteen starts.

## How much each store can grow

- `pilot.log` is at most 40 MB, and the Gnomon worker's log at most 10 MB.
- The activity timeline keeps 7 days by default.
- In memory: the conversation keeps its last 6 turns and the last 20 turn results; Live keeps its last 20 remarks;
  notifications held for a window that is not connected are capped (`MAX_ATTENTION_NOTIFICATION_BUFFER`).
  The simulated soak found nothing else growing; the weekly real soak's result is to come.
- Never pruned by Heliox on its own: the audit log, the durable task and checkpoint tables, and the experience
  ledger. Their sizes and the warning are in the Disk and storage table above.

Measured over a scripted day of 200 requests (`daemon/benchmarks/store_growth.py`: the real request path with the
real stores in a temporary folder, a fixed planner, no model or network; half one-step reads, half a write then a
read), on the development laptop (Windows), 12 November 2026:

| Store | Bytes per request | Per day of 200 requests | Per year at that rate |
|---|---|---|---|
| Audit log (`audit.jsonl`) | 1,099 | 215 KB | 77 MB |
| Durable tasks (`durable_tasks.db`) | 4,997 | 976 KB | 348 MB |
| Checkpoints (`workflow_checkpoints.db`) | 2,048 | 400 KB | 143 MB |
| Experience ledger (`experience.db`) | 12,902 | 2.5 MB | 898 MB |

At ten times the requests (2,000) each store costs the same bytes per request, within 2 % (audit log 1,099 and 1,099;
durable tasks 4,997 and 4,954; checkpoints 2,048 and 2,087; experience ledger 12,902 and 12,947), so the growth is
linear and the yearly figures hold as far as that shows. Same machine and day;
the weekly soak workflow repeats it on all three systems (`store_growth_check.py`).

None passes 1 GB a year at that rate, so the size warning is the answer for now. The experience ledger is the one to
watch: it passes 1 GB a year above about 230 requests a day, or with plans of more steps than this mix.

## By system

- **Windows:** a virtual environment's `python.exe` is a launcher that starts the real interpreter as its child. The
  app and the Gnomon supervisor therefore kill the process together with its children, so no daemon or worker is
  left holding the port or the graphics card.
- **macOS and Linux:** the virtual environment's `python3` is the interpreter itself. Worker processes end when the
  process that started them dies (their pipe closes, and a parent watch notices): in the Real faults job (CI on
  008f1a0) the worker was gone 0.1 s after its parent was hard-killed, on ubuntu, macOS and Windows. A folder made
  read-only keeps working for files that are already open, so the first failure shows when SQLite creates a new
  file.
- **Linux and macOS:** the runtime folder (`/run/user/<uid>/heliox-os`, `~/Library/Caches/heliox-os/runtime`) can
  be emptied by the system, at every reboot on Linux. Only the tokens live there now; the learner's key is in the
  data folder, so its saved state still matches after a reboot.
- **Apple Silicon:** memory is shared with the graphics processor. The question is free system memory, and Gnomon is
  not supported (no CUDA).

## Not covered

- A real GPU reset under load is not tested: the card that would show it is failing, and stress runs are not
  allowed on it. Gnomon's real model was never loaded through the worker during this work.
- A real CUDA out-of-memory error or driver error in Gnomon's or the voice's worker; only a kill was run for real.
- The app restarting a daemon that really crashed has not been run on any system, nor the hang rule killing a really
  stuck daemon. The Rust unit tests run in CI on ubuntu and macOS; on Windows they are compiled in CI and
  type-checked and linted on the development laptop, not run.
- A second real launch of the app: the bring-forward, the "not answering" dialog and the take-over after a minute
  have not been seen on screen on any system.
- A real sleep and wake has not been tested; the clocks are injected.
- The risk gate's 5 s wait for the learner, and "One moment, Heliox is still starting.", have not happened on a real
  start.
- Stopping the daemon with the voice worker or Gnomon's worker running; the runners start neither.
- The durable task and checkpoint tables and the experience ledger have no size bound and no archive: archiving them
  could let a finished action run twice, break undo, and change what the learners read. Only their size is shown.
- A network that really goes away, a real captive portal's redirects, and providers changing their error bodies.
- On Windows a connect to the claimed, not yet listening port fails by timing out (about 2 s of SYN retries) rather
  than at once; the window then retries as it does for any refused connect.
- Logs at their real size limits; rotation is tested at small sizes.
- Recovery after the kernel remounts a failing drive read-only: that needs the drive unmounted and checked.
- The full disk, read-only folder and locked keychain checks run on one system each (ubuntu, macOS); Windows has
  only the fakes for them.
